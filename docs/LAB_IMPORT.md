# Structured lab-file review · Batch 21

This locally verified batch builds on the reviewed lab model rather than treating parsed rows as confirmed measurements. Publication is recorded in the handoff checkpoint. The full product goal remains active.

## Delivery

Library → Add document → **Import lab results** accepts UTF-8 CSV/TSV with headers or a JSON array of flat row objects. Delimited files use comma for CSV or tab for TSV by default; an explicit comma/semicolon/tab choice supports regional exports without guessing from result punctuation. Column mapping supports real export headings rather than requiring a fixed Lumen schema. Exact unambiguous headings may be suggested; the person checks the mapping, selects one subject group, then reviews included rows and their source cells before saving a new record. No existing records, profile or Health samples are replaced. Assistant sharing starts off.

Preserve literal test/result/unit/reference/flag/laboratory/specimen/method fields. Reported collection wording and status remain literal optional fields; complete ISO calendar days can seed an editable day proposal, while other date wording is retained without guessing its interpretation. Null/missing fields stay missing. JSON numeric spellings, including trailing zeros and exponents, are retained without floating-point conversion. Boolean tokens are literal values, never converted into numeric zero/one or clinical meaning.

Input bounds: 2,000,000 bytes, 64 columns and 1,024 nonblank data rows. Delimited files require a first row of unique, visible headers; Lumen does not infer missing headers. Malformed files are rejected as a whole, and ambiguous suggestions remain unmapped for explicit selection. Only physically blank CSV records are counted separately; explicit empty cells/rows are not silently discarded. At most 256 reviewed rows and 200,000 combined source/metadata characters can be saved per record, with separate byte bounds for Unicode text. Oversized/invalid rows remain visible and block saving while included; they can be excluded explicitly. No silent first-N import or clipping is permitted.

Subject mapping is independent of result fields. Different literal subject values, including blank subject cells, remain separate groups. The person explicitly chooses a group and confirms the intended person; there is no automatic identity inference. If no subject column is mapped, the UI says so and requires checking the original. Excluded rows, other subject groups and unmapped columns are not copied into the saved record or assistant context. A mapping can be changed before review; returning after row edits requires discarding that draft rather than silently rebuilding it.

The saved source body is a Lumen layout of selected mapped cells, retaining each original token spelling and field/row location. It is labelled as mapped cells, not a contiguous original-file excerpt. A compatible import receipt retains filename, full input SHA-256, format, read time, mapping, selected original row numbers and subject choice. Keep the original file separately. Row corrections remain separate from the mapped source cells; source editing afterward uses the existing changed-source/stale-metadata rules. Historical import origin stays historical when later manual rows are added or removed.

Reading/parsing runs off the main actor, supports cancellation and never creates a record by itself. Security-scoped/coordinated reads are bounded; no permanent private file mirror or remote request is needed. A late result after cancellation cannot replace another draft. Saving uses checked storage, stable draft identity, a duplicate-file decision and fresh review acknowledgement. Cancel/swipe protects edits. Backups/readable exports/Markdown preserve compatible provenance; older lab records decode without invented file origin.

Duplicate detection uses the full input-file hash across both lab and general record imports. A lab file previously saved through either route requires an explicit separate-copy decision. Matching titles, result values or presumed patient identity do not establish a duplicate.

## References and open scope

[RFC 4180](https://www.rfc-editor.org/rfc/rfc4180) informs quoted CSV fields and embedded line breaks; this implementation also accepts LF/CR and applies the same quoting rules to TSV. [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259) informs strict JSON syntax and literal numeric tokens. This is a bounded flat-table import, not FHIR ingestion, automatic PDF/OCR table interpretation, unit normalization, clinical interpretation or a comprehensive lab-format claim. Those and longitudinal comparison, real clinical accuracy, physical devices, live providers and release governance remain open.

## Compatibility and review refinements in progress

Absent optional timing/status/import-row fields retain the exact published Batch 20 reference text and content fingerprint. An upgrade must not mark an unchanged earlier lab reference as changed merely because new optional metadata exists. Known new fields do enter the fingerprint. The original generated cell-layout hash is retained independently of later review hashes: only an unchanged original layout can be labelled Original source cells; edited-source review keeps its historical file receipt and uses the general saved-source label.

Changing a delimited-file separator leaves Continue disabled until the shown columns were read using that separator (or the choice is returned to the already-read separator). Native menus use full-height multiline labels at actual XXXL. Reported status and raw collection wording appear before row inclusion, including explicit unknowns. The intended-person action has a visible disabled state until its check is on. Result pages contain ten rows, with first/next/last navigation and retained exclusions; Include all / Exclude all changes the temporary draft only. Combined text/byte overflow gives the record-size recovery action, rather than incorrectly blaming a single source row. Native verification covers these refinements; see the precise source boundaries below.

CSV syntax is read by Unicode scalar so a combining mark at the beginning of a cell cannot merge with and hide its preceding separator or opening quote. Decoded values and raw tokens retain the original scalar sequence; CRLF inside quoted cells remains literal, while CRLF outside a cell ends one record. A failing regression exposed this defect before the parser correction.

Later manual results inherit that historical receipt without an invented original file-row number.
