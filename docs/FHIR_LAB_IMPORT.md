# Reviewed FHIR lab exports · Batch 23

Reviewed local FHIR R4 JSON import is implemented and verified within the scope below. Publication and storage cleanup are recorded in the handoff and verification checkpoint. The full product goal remains active; a reviewed file import does not establish clinical validity or authenticate its source.

## Import contract

Add an on-device reviewed import for FHIR R4 JSON lab exports alongside the existing flat-table importer. Accept standalone resources and Bundles, retain the original file identity, and account for all entries before proposing results. The chosen R4 import mode is not proof that an arbitrary file conforms to every FHIR profile. Do not fetch references, paging links, attachments or terminology services. Keep the original file separately.

Prepare result proposals from Observation values/components and DiagnosticReport result relationships. Keep test coding, quantity system/code/display, status, interpretation, every reference-range representation, effective/collection wording, specimen, performer and report relationships separately traceable to their original JSON pointers and tokens. Support quantities/comparators, qualitative and other literal value forms; unsupported or oversized content remains visible with a specific reason and explicit exclusion. Do not turn missing values, booleans, coded results, ranges or sampled data into invented scalar measurements. A partial date or timestamp does not become an inferred calendar day. Issued/import/review timestamps never stand in for collection.

The resource graph resolves exact local fullUrl identities, REST-base-relative references, scoped contained references and explicit resource versions. Logical identifiers require an exact issuer/system and value. Duplicate matches stay ambiguous; an absent requested version never falls back to another. A display name alone never links people. Do not infer an Observation's person, collection time, specimen or laboratory transitively from a linked DiagnosticReport. Show supplied report context separately, including mismatches and unknowns, and require an explicit intended-person decision before review. Conflicting people cannot be silently mixed.

Inventory includes request/response-only entries, deletions, unsupported resource types, missing/ambiguous links and pagination. It must distinguish entries from result proposals. No silent first-N input or proposal prefix. Bound the input to 2 MB, 1,024 entries/resources, 64 JSON nesting levels and 100,000 values; keep cancellation checks during parsing/indexing. Bounds are ceilings, not goals. Do not save a partial parse. Unknown modifier extensions or implicit interpretation rules block automatic result proposals where they could change meaning.

The native flow must make file coverage, person selection, result selection/corrections, full original source fields and omitted content reviewable before saving. Reuse existing complete-value text editors and protected dismissal. Changes reset acknowledgement. Saving uses checked storage and stable draft identity; exact-file duplicates need an explicit separate-copy decision. No source record, personal profile or Apple Health sample is overwritten. Sharing starts off.

Persist compatible optional FHIR provenance with reviewed records and their retained import receipt, including when every transcription is later removed. Original source coding stays historical when reviewed fields are corrected. Existing records and fingerprint goldens must stay unchanged when new metadata is absent. Preserve typed provenance in actual encrypted/readable backups, Markdown, saved comparisons and retrieval. Repeated versions/exports of a known original observation must not manufacture independent measurements; values that are declared qualitative/structured must remain so in history. Comprehensive coding/UCUM normalization and clinical interpretation remain separate work.

## Integration invariants

Keep the FHIR receipt and per-result provenance typed and separate from the flat-table receipt. Existing `importRow` values require a matching table receipt; do not reuse that field or label FHIR resources as original CSV cells. Retain original test/unit coding alongside corrected review text, without changing absent-metadata legacy reference strings or fingerprints. Include original resource/version/component identity in duplicate/revision handling so repeated exports do not imply new independent measurements.

FHIR effective time is a clinically relevant time, not automatically specimen collection time. Preserve both roles separately. Do not place an effective timestamp into `collectedOn` simply to make the existing collection-day chart accept it. If effective days become timeline points, extend the date-role model and native labels explicitly, preserving original offset/precision and keeping partial/unknown dates literal. The current graph does not derive any clinical day.

A graph read is not result eligibility. Proposal validation still needs required code/status and declared value forms, component-specific reference information, known error/cancellation states, interpretation rules, subject conflicts and complete coverage. The graph intentionally retains unknown resource types and request/response-only entries; result extraction must account for them without claiming that each entry is a measurement.

## Primary references read 31 October 2026

- [HL7 R4 JSON](https://hl7.org/fhir/R4/json.html): structured input uses UTF-8 and unique, case-sensitive fields. Preserve number lexemes and original source ranges rather than passing values through floating point. The parser is bounded general JSON; later proposal validation supplies the FHIR-specific checks.
- [HL7 R4 Bundle resolution](https://hl7.org/fhir/R4/bundle.html#references): resource identities are distinct from entry order. Relative links use an applicable service base; version-specific links match resource versions. Ambiguity may be reported as an error. Paging/deletion entries must remain visible in file coverage.
- [HL7 R4 references](https://hl7.org/fhir/R4/references.html): references can use literal URLs, contained fragments or logical identifiers. Subject context generally does not propagate across linked independent resources. Lumen keeps supplied context and unknowns visible instead of treating a matching display label as identity.
- [HL7 R4 Observation](https://hl7.org/fhir/R4/observation.html): result values have different declared forms, and components can carry their own values and reference information. Those distinctions must survive extraction; qualifiers and non-scalar forms cannot be flattened into unqualified numbers.
- [HL7 R4 DiagnosticReport](https://hl7.org/fhir/R4/diagnosticreport.html): a report can connect observations and additional report context. Preserve that relationship separately from the individual result's directly supplied facts.
- [HL7 R4 datatypes](https://hl7.org/fhir/R4/datatypes.html): a Quantity carries its comparator and distinct unit display/system/code fields. Those original fields belong in the review/provenance rather than an inferred unit conversion.

## Batch 25 extension · NDJSON · verified

The same review flow now accepts a local `.ndjson` file with one same-type FHIR resource per physical line, preserving exact complete input bytes, source tokens and absolute byte ranges. A malformed line rejects the whole file; no partial prefix is proposed. LF/CRLF, initial BOM and a final line without newline are supported. Bare CR, blank/multiline/Bundle/mixed-type lines, duplicate keys and manifest objects are rejected. Existing JSON mode does not guess NDJSON after a parse failure.

Line locations are `/line/N` followed by a within-line field path. Exact typed relative IDs resolve only inside the selected file; duplicate IDs remain ambiguous and versioned references require the exact version. No server base or companion Patient is inferred. Known revisions retain one file-scoped event identity, preventing them from silently becoming independent measurements. Sharing, correction/original separation, receipt-only duplicate identity and backup compatibility remain.

Logic passes1,294 checks; current BuildR9/ReleaseR5, reader probe, full compact lifecycle and continuing Round3 design acceptance pass. The older Batch23 evidence above proves its earlier JSON scope; it does not certify this extension.
