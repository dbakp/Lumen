# Question-based Library retrieval

Batch 14 replaces the five-most-recent, first-3,000-character record block in assistant requests with a local question-based search. Batch 19 adds optional English related-topic ranking beside that keyword path; see [local related-topic search](SEMANTIC_SEARCH.md). Neither route extracts structured labs or creates clinical measurements.

## Search and consent

Only documents with **Use in assistant** enabled enter the index. Each question builds an in-memory SQLite FTS5 index on a cancellable background task. SQLite temporary storage is also memory-only. There is no persistent duplicate search database or remote embedding/search service. The optional encoder keeps a bounded private RAM cache; generic downloaded model/runtime files are separate from health records and excluded from backups. The selected AI provider still receives the existing current health summary and conversation context plus the selected Library excerpts; this is not a claim that the whole assistant runs locally.

The lexical search uses Unicode tokenization, case/diacritic folding, bounded English stop words and longer-word prefixes. It ranks title and body matches, selects at most four non-overlapping passages, and limits each document to two passages. Paragraphs are split into 900-character windows with a 120-character overlap. The current plan status and checklist, including completion and planned calendar days (or legacy UTC due dates), accompany a saved plan's prose. Unchanged imported text can retain reviewed page numbers; text edited after review uses excerpt locations instead. These locations describe saved text, not verified original-file pagination.

Limits per question: 5,000 shared documents, 20 million characters, 80 MB of UTF-8 text, and 30,000 indexed passages. A document is limited to 200,000 characters/1 MB and 1,000 checklist steps; titles/sources and passage byte sizes are separately bounded. Coverage counts and an explicit limited-search state accompany results. Title matches are prioritized before global limits. No match does not establish that information is absent. English lexical matching is not semantic retrieval or a clinical accuracy guarantee.

The app checks consent and content again after the background search and before calling the provider. A changed selected record asks for a new question. If a request has already reached a provider, changing a local switch cannot recall that request. Provider use follows the existing user selection; the recorded provider is captured before the asynchronous search.

## Replies and references

Literal lookup keeps the full bounded selection, up to four excerpts and two per document. Later related-topic results must not disappear behind leading keyword matches. Selection method and actual comparison coverage accompany new references; missing older selection metadata stays unrecorded. Topic similarity is not proof that an excerpt answers a question. Referenced Markdown sharing preserves that method/limit disclosure as well as exact text.

Each selected passage gets a fresh request-specific identifier. The provider receives untrusted JSON reference blocks and instructions to cite only those exact identifiers. Lumen converts recognized identifiers to visible numbers. Unknown, stale and bare numbered reference markers become **reference unavailable**, never a link to an unrelated record. Model-supplied Markdown destinations attached to these markers are removed; a Library number cannot become an arbitrary external link. This checks reference identity; it does not establish that a model's claim is supported, medically correct or complete.

**Library for this reply** distinguishes text shared with a provider from text its answer actually cited. **Library matches** identifies the built-in fallback: literal saved-text excerpts, no model interpretation. Built-in flexible plans and urgent-symptom guidance retain their existing precedence. Search failure asks for retry instead of pretending the Library was searched successfully. A fallback label identifies the source of the displayed answer; a failed provider attempt may already have received the question and selected context. It does not imply that no remote request was attempted.

Successful model replies keep the selected provider packet; literal lookups keep the excerpts they return. Each retained passage includes its exact text, document identity/title/source, content fingerprint, character range, page/excerpt location, selection time and document update time. Tapping a reference shows this snapshot and a route to today's Library version, with explicit changed/sharing-off/deleted states. Dates are document/selection dates, not dates of a clinical observation. Saving a reply or generated plan carries its source map; sharing a document or conversation appends only the referenced excerpts, not unused provider context. New metadata is optional for older storage and is validated in both backup formats.

## History, withdrawal and copies

A previous source-bearing reply is replayed to a provider only while every selected source still has matching content and sharing permission and appears in the new question's selected context. Source numbers are mapped to the new request's identifiers. Follow-ups can retain the latest reply's exact current sources; they do not jump over a later guide reply to an unrelated older record. This policy deliberately favors omission over silently sending stale text.

Earlier replies without a source map stay visible but are omitted from new provider history. Their interface says so and offers **Quote in new question**, which places a bounded quote into the editable composer without sending it. The prepared quote ends with an editable question cue, avoiding the composer's newline-to-send behavior. User messages remain conversation context; explicitly quoting and sending text is a new user disclosure.

Turning sharing off or deleting the original Library document stops future retrieval and replay of its source-bearing replies. It does not erase excerpts already stored in conversations, independently saved Library copies, exported files, backups or a provider's earlier requests. The interface explains retained copies. Delete the conversation and saved copies separately; external copies remain under their holders' control. New restore documents still start with sharing off, following the existing backup policy.

## Verification boundary

Production-logic checks exercise real SQLite FTS5, relevance beyond five newer records and beyond 3,000 characters, page locations, Unicode offsets, current checklist state, private-record exclusion, fresh/stale/fabricated citations, follow-up remapping, consent/edit/delete gates, legacy history, cancellation, bounds and backup/export compatibility. 439 production-logic checks pass. The final native three-case suite, separate daily/encrypted-backup regression, native storage read-back, all-target builds and three-round design sign-off are recorded in VERIFICATION.md. Synthetic data only. Live Apple/OpenAI inference, semantic grounding quality, multilingual retrieval quality, physical-device memory/performance and VoiceOver remain separate gates.

Scheduled plan steps include their current literal planned calendar day when present, rather than converting that date into an observation timestamp. Older steps keep their existing absolute due date. Current completion/date edits remain part of the content fingerprint, so earlier source-bearing replies cannot silently become evidence of a changed schedule. See [Scheduled plans](SCHEDULED_PLANS.md).

## Reviewed lab fields

Current, individually reviewed lab transcriptions join the same consent-filtered canonical record text. Reported values/units/reference wording/flags remain literal; missing fields stay unknown. Correcting a structured field changes the source fingerprint. Appended metadata cannot inherit a PDF page number or introduce page headings; it is identified as a saved-text excerpt. If the source body changes, historical lab fields remain visible for review but are withheld from future structured retrieval. Source text and earlier independent replies/copies retain the existing policy. See [Reviewed lab records](LAB_RECORDS.md) for native review, compatible backups and exact verification scope.


## Literal identifier lookups · Batch27

Recognized explicit references constrain both keyword and optional topic search before ranking. Examples: `sample ID LAB-42`, `report number FE-Q7`, `invoice AF-740`, and a quoted numeric-bearing token such as `"TEST-AX1"`. A strongly shaped sample reference such as `sample TEST-AX1` also qualifies. Ordinary new-topic questions about B12, HbA1c, COVID-19 or ICD-10 stay topic questions. Use an explicit ID/code/number label for an ambiguous reference; this is a bounded English intent parser, not general medical-code normalization.

The entire labelled field is checked before token extraction. Unsupported leading punctuation (`sample ID /TEST-AX1`), spaced quoted values (`invoice "AF 740"`) and attached composites receive a format response, rather than silently reverting to topic search. Ordinary sentence/field punctuation remains distinct from the identifier. In the regular built-in assistant, an explicit identifier and its unqualified follow-up chain retain Library lookup intent even after a no-match reply; this does not depend on a test reply override.

The selected saved title or exact prepared excerpt must contain the complete token, compared without case distinction. Leading zeros, version suffixes and separator characters remain significant; hyphens/Unicode dashes/underscores/slashes are not silently substituted. Original title/text/bytes, fingerprints, offsets and saved source snapshots are never rewritten. A source title can identify a Library record; matching a token does not verify clinical authorship, server identity, the intended person, or that a result belongs to the requested specimen. It is still necessary to read the original and check whether it supports the question.

Combined explicitly labelled/quoted references and contiguous numeric-bearing identifier lists require every recognized identifier to occur within the prepared, consented search coverage. A missing requested ID cannot be replaced by whichever other ID exists. When all are present, source slots are reserved before topic fusion can fill the packet with one record. Existing four-passage/two-per-document/non-overlap limits remain; if the requested set cannot fit, the assistant asks for fewer identifiers rather than returning a partial packet. This is not a guarantee that arbitrarily many records can be compared in one reply.

A newly specified identifier replaces prior follow-up constraints and carried passages. While already in an identifier lookup, a complete new code-like token in a follow-up also replaces the earlier token. Consecutive unqualified follow-ups retain the original scope; a new non-follow-up topic does not inherit it. No abbreviated-ID expansion or clinical equivalence is inferred. Sharing withdrawal, source edits/deletion, history replay checks, encoder-cache pruning and current settings checks still apply. Earlier source snapshots and independent copies remain historical under the existing retained-copy policy.

The complete question is inspected up to32,000 UTF-8 bytes, at most16 recognized identifiers, at most96 characters each. Unsupported/over-limit explicit forms stop without truncating to a neighboring ID. Separate messages identify question length, identifier length, count, format or source-packet capacity and offer the relevant recovery. Nonmatching source windows still count toward the original index bounds and cancellation checks, so filtering does not bypass work limits. No match remains limited to the documents/text searched; it does not establish absence.

Source matching locates complete identifiers in the original title/paragraph before preparing excerpts. Only an occurrence entirely contained in a selected window can establish coverage; a version suffix clipped at the900-character boundary cannot make its prefix eligible. Quoted single-token fields retain their full punctuation and cannot also emit a shorter unquoted identifier. Overlapping windows retain complete occurrences with original grapheme offsets.

No search-model/cutoff replacement or persisted-schema change is part of this feature. Batch26's medical candidate remains research. Live-provider entailment, multilingual intent coverage, full source authenticity/clinical validation, physical-device performance and release gates remain separate.
